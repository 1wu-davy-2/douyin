# 后续项目优化方案

> 状态:规划中(未落地)。本文记录后续要做的两条互补主线 + 辅助措施,作为落地依据。
>
> 背景:抖音 403 风控有两套独立成因——**(A) Cookie/状态过期**(时间驱动,与频率无关)、**(B) 请求频率/IP 信誉**(频率驱动)。已上线的风控弹窗(commit `009ab8e`)是"已经中招"后的兜底提示;本文件是"前置减负",从源头降低 403 触发率。

---

## 一、主线 A:msToken 自动刷新(续火花方案)

**状态:已在另一分支开发并合并,本文仅记录其定位与衔接约定。**

### 解决什么
治成因 (A)。浏览器 Cookie 是快照,抖音服务端的 `msToken`/`verify_fp` 等字段由前端 JS 分钟级轮换;复制出来的 Cookie 几分钟到几十分钟后,post 列表接口(`/aweme/v1/web/aweme/post/`)就判定"状态对不上"→ 403,而 `/profile` 仍能通(半失效 Cookie 的典型分裂)。证据:新粘贴的 Cookie 25 分钟后 /posts 即 403,期间请求量并不大 → 时间驱动,非频率驱动。

### 思路
用无头浏览器(或直接跑抖音前端 JS)持续产出新鲜的 `msToken` 等签名/状态字段,注入 sidecar 的请求头,使 Cookie 快照不再"过期"。与 F2 的 `a_bogus` 签名正交:F2 管请求签名,本方案管会话状态字段的新鲜度。

### 衔接约定(与主线 B 的合并点)
- sidecar 对外契约(`/profile`、`/posts`、`/work`)不变;token 新鲜度由 minter 在 sidecar 内部或上游保证,Go 端无感。
- Cookie 写入路径不变:仍由设置页 PATCH → `data/.cookie` → sidecar 热加载。minter 在此基础上补齐动态字段。
- 风控弹窗(commit `009ab8e`)继续作为最终兜底:minter 也挂了、或刷新失败累积时,弹窗照样触发。

### 待确认(见该分支)
- minter 的资源占用与生命周期(常驻 vs 按需)。
- 刷新失败时的降级:退回静态 Cookie + 触发风控弹窗。
- 与 F2 的集成方式(覆盖 kwargs.headers 还是预处理 cookie 串)。

## 二、主线 B:增量扫描重构(new_count 边界 + count 闸门)

**状态:未落地。本节是落地依据。**

### 解决什么
治成因 (B)。订阅监控稳态下 95% 的 tick 没有新作品,但现行增量扫描每次仍要翻 ≥3 页 /posts 才停——这是对最敏感接口的无效高频调用。重构后每次 tick 降到 0~1 页,直接减负。

### 现状(代码位置)
`backend/internal/scanner/loop.go`:
- `pageCount = 20`(抖音硬限,不可改)。
- 增量停止条件(`!full`):每页 `newN == 0`(整页全已知)则 `consecKnown++`,连续 `incStop`(默认 3)个全已知页才 `termIncremental` 停。
- 即:只要有 ≥1 个新作品,`consecKnown` 就被重置,必须再翻 3 个全已知页才停。

### 目标算法
列表按 `create_time` 倒序、每页 20。每页算 `new_count = 本页 item_id 不在 DB 已知集的个数`:

| 本页 new_count | 含义 | 动作 |
|---|---|---|
| `< 20` | 本页出现了已知作品 → 边界已到 | **停**;累计的 new 即为全部新增 |
| `== 20` | 整页全新 → 可能有更老的新作品 | 翻下一页,继续累计 new |
| `0` 且 `has_more=false` | 到底了 | 停 |

**停止条件用 `new_count < 20`,不要用"第一个已知 item 就停"**。区别在置顶作品:置顶项总在页首且早就在 DB 里,"第一个已知就停"会被置顶骗成"0 新增";而 `new_count` 把置顶算作已知、扣掉它占的名额,剩下多少真·新增一目了然——**对 pinned 天然安全**。

"记忆的最新 20"无需单独存:DB 已有全部 `item_id + published_at`,扫前
`SELECT item_id FROM works WHERE creator_id=? ORDER BY published_at DESC LIMIT 20`
即"上次最新 20"。**零 schema 改动**。

### 收益对比(/posts 调用页数)

| 自上次扫描新增 | 现在(3 全已知页停) | 重构后(new_count<20 停) | 省 |
|---|---|---|---|
| 0 | 3 页 | 1 页 | 3× |
| 5 | 4 页 | 1 页 | 4× |
| 20 | 4 页 | 2 页 | 2× |
| 25 | 5 页 | 2 页 | 2.5× |

叠加下方"count 闸门",订阅稳态(0 新增)从 3 页降到 0 页。

### count 闸门(前置软过滤)
订阅 tick 先拉 `/profile` 取 `aweme_count`(该接口风控宽松):
- count 与上次相同 → 直接跳过 /posts(稳态 95% 走这条,0 次敏感调用)。
- count 变了 → 进入上面的 new_count 边界算法。

**count 只是软信号,不是"新增 N 条"的真相**:创作者删了又发(count 不变)会漏一次,下一次全量扫补回;监控场景可接受。真正的新增数以页 diff 为准。

### 落地改动点
1. `loop.go`:把 `consecKnown`/`incStop` 那段替换为 `new_count < 20 ⇒ termIncremental`(全量 `full=true` 路径不变,仍翻到底)。
2. `scheduler`:订阅触发处加 count 闸门——比对 `creators.reported_work_count` 与上次扫描记录的 count,相同则跳过 /posts(仍可顺手刷新 profile)。
3. 无需迁移、无需改契约、无需改前端。

### 边界情况(必须收口)
- **置顶作品**:用 `new_count` 而非"首个已知"→ 安全(见上)。
- **中途短页**:抖音偶发某页返回 <20 条但非边界。概率低;稳妥做法是"第一页若 `0<new_count<20 且 has_more` 多翻一页确认",多数情况可省。
- **删作品**:检测不到(同现状,只有全量扫软删)。count 下降可作 UI 提示,下载侧无可做。
- **count > 列表实际暴露**(短剧/私密作品):别为追 gap 无限翻页,`has_more=false` 即停,沿用现有 completeness partial 标记。
- **首次扫描**:DB 无已知集 → `new_count` 恒 20 → 自然翻到底,等价全量,无需特判。
- **老作品元数据陈旧**:翻页变少 → 老作品标题/封面被重读刷新的机会变少;归档工具可接受,定期跑全量扫补。

### 验收(单测场景)
`scanner_test.go` 补充:已知集预置后,新增 0/5/20/25 各应翻 1/1/2/2 页即 `termIncremental`,且 `new_count` 累计正确;置顶(item_id 已知但 create_time 最新)不误判为 0 新增。

## 三、辅助措施(可选,主线落地后再考虑)

主线 A、B 已能将风控压力降一个数量级;以下为锦上添花,优先级低。

### 3.1 403 全局退避(用现有 provider_state 表)
首次 403 簇发 → 全局 `risk_paused` 暂停所有扫描 30-60s → 重试 1-2 次;仍失败再升级到风控弹窗(commit `009ab8e`)。区分"瞬时限流(可自愈)"与"Cookie 已死(需换)"。复用现成但未启用的 `provider_state.risk_paused`/`paused_until` 字段。

### 3.2 订阅串行 + 放宽页间隔
- `scan_concurrency=1`(订阅场景)→ 同一时刻只有一个博主的请求在飞。
- 订阅页间隔放宽到 5-10s(全量扫描保持 2-3s,用户主动触发等得起)。需先把设置项 `scan_page_delay_ms` 上限从 10000 放开。

### 3.3 AIMD 自适应页间隔
正常 2s 跑;遇一次 403 乘性退避到 10-15s 维持若干页;连续成功后线性回落。与 3.1 搭配最自然。

| 优先级 | 事项 | 治 | 工程量 | 风险 |

## 五、明确不做 / 取舍

- **不改 `MAX_COUNT=20`**:抖音服务端硬限,传更大也只回 20。
- **不追 count > 列表暴露的 gap**:短剧/私密作品列表接口本就不吐,追不完;`has_more=false` 即停,partial 标记如实反映。
- **不为元数据新鲜度翻额外页**:老作品标题/封面变陈旧接受,定期全量扫补。
- **不替主线 A 定实现细节**:见其分支,本文只约束衔接契约。
